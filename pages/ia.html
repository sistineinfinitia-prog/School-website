IB DIPLOMA PROGRAMME • COMPONENT 03

Internal Assessment (Computational Solution)

Official coursework specification for the redesigned IB Computer Science syllabus (First Assessment May 2027). A 35-hour individual engineering project marked out of 30 marks, weighted at 30% for Standard Level and 20% for Higher Level.

Showing 5 Assessment Criteria • 30 Marks Total • Redesigned 2027 Syllabus Framework
2027 Syllabus Paradigm Shift: No External Client Required Official Curriculum Update

A major update in the redesigned IB Computer Science curriculum is that students are NO LONGER required to have a real individual, external third-party client, or formal business contract. You do not need formal client interview transcripts, business sign-off letters, or workplace advisors.

Instead, the IA is defined as an authentic computational solution to an identified problem. The core requirement is that you identify a real-world problem or intellectual challenge that demands computational thinking, algorithmic complexity, structured data modeling, and empirical verification. The "user" can be a user group, school club, academic peer cohort, simulated community, or even an optimization tool for personal scientific exploration.

A

Criterion A: Problem Specification

Problem scenario, computational justification, user requirements & testable success criteria

4 Marks 13.3% of IA ~400–500 Words

Establish a clear, authentic problem scenario within a justifiable computational context. Define detailed functional and user requirements, analyze technical feasibility, and formulate 5 to 8 specific, measurable, and testable success criteria that anchor the entire project lifecycle.

Max Marks: 4 • Core Focus: Chain Foundation
A.1

Official 2027 Markband Descriptors

Examiner Matrix
0 Marks Unmet

The student's submission does not reach any standard described by the markband descriptors below.

1–2 Marks Partial / Limited

The problem scenario is vaguely described or the computational context is weak or inappropriate. Solution requirements are generic, subjective, or incomplete. Success criteria are missing, purely qualitative, or untestable.

3–4 Marks Excellent / Top Standard

The problem scenario is thoroughly described and compellingly justified within an appropriate computational context. Requirements are comprehensive and explicitly defined. A robust set of specific, testable, and measurable success criteria is established.

A.2

Mandatory Deliverables & Evidence

Checklist
1
Authentic Problem Scenario

Clear narrative describing the operational bottleneck, current manual inefficiencies, and the scope of the problem to be solved.

2
Computational Rationale

Explicit justification explaining why existing off-the-shelf software (e.g. basic spreadsheets) is unsuitable and why bespoke programmatic logic is needed.

3
User Needs & Constraints

Functional requirements, input data structures, expected system throughput, technical constraints, and target user profile.

4
Testable Success Criteria Matrix

5 to 8 individually numbered criteria [SC1..SCn] with precise quantitative thresholds that will be tested in Criterion D and evaluated in Criterion E.

A.3

Examiner DO's vs DON'Ts (With Concrete Examples)

Scoring Strategy
DO EXEMPLARY STANDARD

Write Testable, Quantitative Criteria

State measurable parameters, specific boundary numbers, response time limits, and verification methods so examiners can confirm achievement objectively.

[SC-01 SPECIMEN] "The system must authenticate users by hashing input passwords using SHA-256 with salting, locking the account for 300 seconds after 3 consecutive failed login attempts."
[SC-02 SPECIMEN] "The timetable generator algorithm must resolve room allocations for 40 teachers without conflict in under 2.5 seconds, outputting a valid schedule to SQLite."
DO COMPUTATIONAL JUSTIFICATION

Justify Algorithmic Need

Demonstrate that the problem requires algorithmic complexity, automated parsing, multi-relational database integrity, or computational automation.

[RATIONALE SPECIMEN] "A standard spreadsheet cannot enforce relational referential integrity between student prerequisite courses and course sections, resulting in manual schedule clashes that take 20+ hours each term to resolve."
DON'T COMMON PITFALL

Write Vague, Subjective Descriptors

Never use untestable subjective adjectives like 'user-friendly', 'fast', 'visually appealing', or 'secure' without measurable parameters.

[UNTESTABLE ANTI-PATTERN] "The program should be very easy to use and intuitive, and students will love using the UI." — (Pure opinion; untestable and penalized by moderators).
DON'T FEASIBILITY VIOLATION

Over-Scope or Invent Impossible AI Goals

Avoid unrealistic claims that cannot be proven or developed within the 35-hour coursework allocation.

[UNFEASIBLE ANTI-PATTERN] "The app will predict global cryptocurrency price movements with 100% precision using an advanced neural network." — (Unrealistic, unmeasurable, unmanageable).
Examiner Moderation Insight for Criterion A: Number each success criterion as SC-01, SC-02, up to SC-07. The external moderator will trace these exact tags directly into Criterion C (Test Strategy Matrix), Criterion D (Executed Test Logs & Screenshots), and Criterion E (Evaluation Appraisal). If an examiner sees unnumbered or narrative criteria, your coursework risks losing marks across multiple criteria due to broken coherence.

B.3

Examiner DO's vs DON'Ts (With Concrete Examples)

Scoring Strategy
DO ENGINEERING AUTHENTICITY

Log Real Engineering Hurdles & Fixes

Examiners want to see the iterative engineering struggle. Document authentic debugging breakthroughs, database schema alterations, and refactorings.

[AUTHENTIC TASK LOG EXCERPT] • Task: "Build recursive tree search in Python"
• Sprint Date: "Oct 14, 2026 (Est: 3h, Actual: 4.5h)"
• Hurdle: "Encountered RecursionError on unbalanced binary trees with 1,200 nodes."
• Resolution: "Implemented iterative traversal stack using deque, reducing memory overhead to O(1) auxiliary space."
DON'T SUPERFICIAL LOGGING

Submit a Retrospective Fake Diary

Examiners spot fake diaries immediately. A log that has no hurdles, smooth round hours, or generic phrases loses credibility.

[FABRICATED RETROSPECTIVE] • "Week 1: Thought of idea. Everything went well."
• "Week 2: Coded the entire program without errors."
• "Week 3: Tested and finished." — (Zero technical specificity; capped at 1-2 marks).
Examiner Moderation Insight for Criterion B: Ensure your decomposition diagram explicitly separates concerns. If you present a diagram with only 2 boxes ("Code" and "Database"), you will be capped at 1–2 marks. Show distinct modules: Data Model, Business Engine, Validation Filter, Presentation Layer, and File I/O.

C.3

Examiner DO's vs DON'Ts (With Concrete Examples)

Scoring Strategy
DO COMPREHENSIVE TEST DESIGN

Plan Normal, Boundary & Abnormal Data

A test plan that only tests valid inputs cannot score above 4 marks. Include boundary limits and deliberately invalid inputs to verify defensive exception handling.

[TEST MATRIX SPECIMEN - SC-01] • Test T1 (Normal): Input "Passw0rd123!" → Auth success, redirect to dashboard.
• Test T2 (Boundary): Input password with exactly 8 chars → Accepted.
• Test T3 (Boundary): Input password with 7 chars → Error "Min 8 chars required."
• Test T4 (Abnormal): Input SQL injection "' OR '1'='1" → Sanitized and blocked.
DON'T INFORMAL MODELING

Draw Informal Sketches or Box Dumps

Do not use generic unformatted boxes with no method parameters, attribute types, or arrows. Hand-drawn unreadable sketches are penalized.

[DEFECTIVE DIAGRAM] Box with just "User" pointing to "Database" with an unlabelled line. No method signatures like +login(u: str, p: str): bool, no primary keys. — (Instantly caps Criterion C at 2 marks).
Examiner Moderation Insight for Criterion C: Remember: Criterion C is the plan, not the result. Do not paste screenshots of test results in Criterion C! Criterion C contains the blank test matrix with planned inputs and expected outcomes. The actual screenshots and executed results belong in Criterion D.
D

Criterion D: Development & Algorithmic Complexity

Working computational solution, algorithmic complexity, technical justifications & empirical test evidence

12 Marks 40% of IA (Heaviest Weight) ~800–1,200 Words + Code Excerpts

The central core of the IA carrying 40% of the entire grade. Candidates must prove non-trivial algorithmic mastery, OOP modular structure, defensive programming, and rigorous technical decision-making. Includes annotated excerpts of 4–6 core algorithms and empirical test execution evidence (actual screenshots and logs) validating every single success criterion.

Max Marks: 12 • Core Focus: Algorithmic Complexity & Empirical Proof
D.1

Official 2027 Markband Descriptors (12 Marks)

4-Tier Assessment
1–3 Marks Basic Functionality

The software demonstrates limited functionality. Trivial programming techniques are used (linear procedural scripts, basic if-else logic). Code lacks modularity. Technical decisions are unjustified. Testing evidence is minimal or incomplete.

4–6 Marks Partial Complexity

The solution is partially functioning with moderate complexity. Basic modular structures are implemented. Code excerpts are present with minimal annotations. Testing evidence covers some criteria but lacks boundary or abnormal cases.

7–9 Marks Competent Engineering

The computational solution is fully functional and exhibits sound algorithmic complexity (custom OOP classes, search/sort, structured file or database persistence). Modular code with clear structure. Sound justification of technical decisions. Good testing evidence validating most success criteria.

10–12 Marks High Mastery / Top Band

High-level computational solution demonstrating advanced algorithmic complexity (custom recursion, dynamic programming, custom tree/graph algorithms, relational queries, defensive validation). Elegant, modular OOP architecture. Thoroughly annotated code excerpts justifying technical trade-offs. Exhaustive empirical testing evidence (screenshots, terminal logs, database state changes) confirming ALL Criterion A success criteria across normal, boundary, and abnormal cases.

Mandatory Deliverables & Evidence

Checklist

Evidence of Algorithmic Complexity

Demonstration of non-trivial computational thinking: recursive algorithms, custom searching/sorting, multi-dimensional data structures, OOP inheritance, or SQL relational joins.

2
Annotated Code Excerpts (4–6 Samples)

High-resolution code snippets with line-by-line annotations explaining algorithm mechanics, defensive exceptions, and time/space complexity.

D.3

Examiner DO's vs DON'Ts (With Concrete Examples)

Scoring Strategy
DO ALGORITHMIC COMPLEXITY

Write Custom Algorithmic Logic

Examiners grade YOUR algorithmic logic, not external library calls. Write custom traversal, mathematical heuristics, sorting filters, or recursive parsers.

[ANNOTATED PYTHON SPECIMEN] # Lines 45-62: Recursive QuickSort with Median-of-Three Pivot
def _quick_sort(self, records, low, high):
    if low < high:
        pivot_idx = self._partition(records, low, high)
        self._quick_sort(records, low, pivot_idx - 1)
        self._quick_sort(records, pivot_idx + 1, high)
# Annotation: Chosen over standard BubbleSort to achieve O(n log n) average time complexity when handling up to 5,000 transaction records (SC-02).
DO EMPIRICAL VERIFICATION

Provide Screenshot Evidence for Every Test

Every row in your testing table must have an embedded screenshot proving that the software actually ran and handled the test case.

[EXECUTED TEST ROW SPECIMEN] Test T3 (Boundary: password length = 7) → Expected: Error dialogue → Actual: UI dialogue displayed: "Password must contain at least 8 characters" → Status: PASS • [See Figure D.4: UI boundary warning screenshot].
DON'T TRIVIAL IMPLEMENTATION

Rely on Black-Box One-Liners

If your program just calls data.sort_values() or calls a third-party AI API with zero student-written logic, you will be penalized heavily in algorithmic complexity.

[BLACK-BOX ANTI-PATTERN] def do_everything():
    response = openai.ChatCompletion.create(...) # 95% of project
    print(response)
(Fatal flaw: zero candidate algorithmic complexity demonstrated; marks capped at 3/12).
DON'T UNANNOTATED CODE DUMP

Dump Unannotated Source Code

Never paste 30 pages of raw code without line-by-line annotations. Examiners will not read raw dumps; they only score annotated snippets.

[BOILERPLATE DUMP ANTI-PATTERN] Pasting 1,500 lines of boilerplate UI button positioning code or standard getter/setter properties without explaining algorithmic significance.
Examiner Moderation Insight for Criterion D: Criterion D is where students gain or lose the most marks in the entire diploma. To reach 10–12 marks, you must show both algorithmic depth (demonstrating why your code is computationally non-trivial) and empirical testing validity (proving with screenshots that boundary and abnormal inputs are properly caught).

E.3

Examiner DO's vs DON'Ts (With Concrete Examples)

Scoring Strategy
DO OBJECTIVE APPRAISAL

Be Honest About Limitations

Examiners award high marks for critical honesty. Acknowledging partially met criteria and explaining technical reasons shows superior academic maturity.

[CRITICAL EVALUATION SPECIMEN] "SC-04 (CSV Batch Import): Partially Met. While the parser successfully processes standard UTF-8 files up to 2,000 rows, it crashes on Windows-1252 encoded strings with accented characters (Test D.12). A dedicated encoding auto-detection filter using chardet should be implemented."
DO TECHNICAL RECOMMENDATIONS

Write Actionable Technical Future Work

Propose concrete software engineering upgrades with named libraries, data structures, or algorithms.

[FUTURE EXTENSION SPECIMEN] "Recommendation 1: Replace synchronous SQLite transactions with an asynchronous connection pool via aiosqlite and introduce a B-tree composite index on (student_id, term_date) to reduce timetable query latency from 850ms to <50ms."
DON'T UNCRITICAL BIAS

Write Blanket Self-Praise

Never write that your program is flawless or that zero improvements are needed. This is an immediate red flag for examiners.

[BLANKET PRAISE ANTI-PATTERN] "My project was a complete success with 100% perfection. All features work amazingly and the user said it was the best software they had ever seen." — (Immediate deduction to 1-2 marks).
DON'T COSMETIC TRIVIALITY

Give Trivial or Cosmetic Suggestions

Avoid superficial wishes like changing button colors or adding generic animations.

[COSMETIC ANTI-PATTERN] "In the future I would make the background blue, add some sound effects, and make it look prettier." — (Zero technical value).
Examiner Moderation Insight for Criterion E: Every single criterion listed in Criterion A must appear in the Criterion E evaluation matrix. If you wrote 7 success criteria in A, there must be 7 rows evaluated in E. If a criterion was not met, state "Unmet / Partially Met" and explain why; examiners reward critical reflection!

1. The Redesigned 2027 Internal Assessment Architecture

The Internal Assessment (IA) for the redesigned International Baccalaureate Diploma Programme (IB DP) Computer Science curriculum—first assessed in May 2027—is an individual computational project that challenges students to solve a genuine problem through algorithmic thinking and software development.

Unlike the legacy syllabus (which was marked out of 34 marks and mandated external third-party client interviews), the 2027 specification is marked out of 30 marks across five unified criteria (A through E). It accounts for 30% of the final grade at Standard Level (SL) and 20% of the final grade at Higher Level (HL), representing approximately 35 hours of instructional and development time.

Criterion Focus & Scope Maximum Marks IA Weighting
Criterion A Problem specification, computational context, user requirements & success criteria 4 Marks 13.3%
Criterion B Problem decomposition, development methodology & chronological task logging 4 Marks 13.3%
Criterion C System architecture modeling, algorithms, UI wireframes & testing strategy 6 Marks 20.0%
Criterion D Working solution, algorithmic complexity, technical decisions & test evidence 12 Marks 40.0%
Criterion E Systematic evaluation against success criteria, user feedback & future extensions 4 Marks 13.3%
TOTAL Complete 35-Hour Computational Coursework Solution 30 Marks 100%

2. The Client Requirement Dispelled: Authentic Problem Solving

A widespread point of confusion among IB students relates to the requirement of an external "client". Under previous curriculum guides, candidates had to identify an external third-party individual or small business and conduct recorded interviews.

In the redesigned 2027 curriculum, an external client is NO LONGER strictly mandated. The IB recognized that finding authentic commercial clients created artificial barriers and resulted in scripted interactions. The 2027 IA refocuses squarely on authentic computational problem-solving.

What matters to IB examiners is whether you are addressing a genuine problem that demands computational thinking. Acceptable project domains include:

  • School / Community Operational Tools: Automated scheduling engines, library asset trackers, sports tournament brackets with conflict resolution.
  • Scientific & Mathematical Simulators: Orbital mechanics visualizers, epidemiological transmission models, ecological predator-prey systems.
  • Algorithmic & Educational Platforms: Interactive sorting/graph algorithm visualizers, adaptive flashcard engines utilizing spaced repetition heuristics.
  • Data Processing & Analytics Utilities: Relational data management systems with custom filtering, data sanitization, and automated PDF report generation.
  • Game Engineering with Algorithmic AI: Strategy board games (e.g. Chess, Connect Four) powered by Minimax algorithms with alpha-beta pruning.

3. The Golden Chain of Consistency (The Core Examiner Principle)

According to top IB examiner reports and RevisionDojo's analysis, the single most critical factor in achieving a Grade 7 (26–30 marks) is maintaining an unbroken chain of consistency across all five criteria. The success criteria formulated in Criterion A must drive every subsequent phase of the project:

Criterion A Specify Criteria Define SC1..SC7
→
Criterion B Plan Modules Sprints to build SC1..7
→
Criterion C Model & Strategy Test plan for SC1..7
→
Criterion D Code & Empirical Test Proof of SC1..7
→
Criterion E Evaluate Status Appraise SC1..7

If an examiner identifies a criterion tested in D that was never specified in A, or if Criterion E evaluates features never tested in D, your coursework is penalized for fragmented planning. Ensure that every success criterion has an identical ID (e.g. SC-01 through SC-07) maintained seamlessly throughout the document.

4. Technical Stack, Language Selection & Data Persistence

The IB Diploma Programme does not mandate a specific programming language. However, the chosen language must support object-oriented programming (OOP) principles, structured data manipulation, and non-trivial algorithmic techniques.

Recommended Programming Languages

Python 3.x is the primary language recommended at Emirates International School Meadows due to its expressive syntax, comprehensive standard library, robust database bindings (sqlite3), and GUI frameworks (PyQt6, Tkinter, CustomTkinter). Java and C# are equally acceptable if students possess advanced fluency.

Data Persistence Mandate

Projects that store data purely in temporary RAM variables (e.g. basic Python dictionaries that reset when the window closes) will be heavily capped in Criterion D. A top-band computational solution must implement structured data persistence:

  • Relational SQL Databases (Best Practice): Local SQLite embedded database with primary keys, foreign keys, and normalized tables.
  • Structured File Serialization: Complex hierarchical JSON or multi-file CSV persistence with automated validation schemas.

5. Academic Integrity & Generative AI Regulations

Emirates International School Meadows enforces the official IB Academic Integrity Policy across all coursework stages. With the rise of Large Language Models (LLMs) and code assistants (ChatGPT, GitHub Copilot, Claude), candidates must strictly adhere to the following rules:

1
Original Code Authorship

All core algorithmic logic, data models, and business logic must be authored directly by the candidate. Using AI to generate entire functions, classes, or documentation violates IB regulations.

2
AI Assistance Declaration

If generative AI is used for conceptual brainstorming, troubleshooting a syntax error, or syntax referencing, the interaction must be transparently cited in an appendix (specifying the tool, version, prompt, and date).

3
Third-Party Library Attribution

Using open-source libraries (e.g. Pygame, NumPy, PyQt, bcrypt) is fully permitted, but they must be explicitly cited in a dedicated library declaration table in Criterion D.

6. Coursework Assembly & Final Submission Checklist

Before submitting your coursework to the EIS Computer Science Department for internal marking and IBO moderation upload, verify the following:

  • • Single PDF Document: The complete written coursework (Criteria A through E) must be compiled into a single PDF document.
  • • Word Count Guidelines: The recommended word limit is approximately 2,000 to 3,000 words across all criteria (excluding code listings, UML diagrams, test data tables, and bibliographies).
  • • Numbered Success Criteria: Ensure all criteria in Criterion A are tagged (e.g. SC-01) and traced verbatim into Criteria C, D, and E.
  • • Empirical Test Screenshots: Verify that every row in your Criterion D test execution table includes an accompanying screenshot showing actual program output.
  • • Anonymity Standards: Remove all student names and school names from the document header and body, retaining only your candidate session code.
